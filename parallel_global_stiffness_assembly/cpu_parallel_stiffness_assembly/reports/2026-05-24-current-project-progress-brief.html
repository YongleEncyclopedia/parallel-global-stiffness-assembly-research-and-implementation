我们正在把有限元矩阵组装做成一套可验证、可复现实验平台

这个仓库关注一个很具体但很关键的环节：在工程仿真里，如何把数百万个单元的局部刚度贡献快速、正确、可复现地汇总成整体刚度矩阵。最新进展是：求解级正确性已经用 MATLAB + CalculiX 闭环验证，Intel Linux 主机上的性能和内存证据也已经重跑到可报告状态。

先把背景说清楚

有限元仿真会把一个复杂零件切成很多小单元。每个单元都能算出一个小的刚度矩阵，但真正求位移、应力之前，需要把这些小矩阵按节点和自由度关系汇总成一个很大的全局刚度矩阵。这个汇总过程就是本项目里的“整体刚度矩阵组装”。

  • 1为什么重要：矩阵组装如果慢，后面的求解器再强也会被前处理拖住；如果内存失控，真实工程网格就跑不起来。
  • 2现在的项目边界：共享内存 CPU 上的并行组装、符号/数值组装拆分、真实工程网格 benchmark，不做 GPU/MPI/非线性接触/商业求解器完整替代。
  • 3当前标准模型：全部正式结果使用 `linear_elastic_solid`，也就是三维小变形线弹性实体刚度模型；`legacy_synthetic` 只保留作历史或极小 smoke。

一句话类比

可以把它想成一次超大规模的“财务合并报表”：每个部门先算自己的账，最后必须按统一科目汇总到总账。难点不是公式本身，而是很多部门同时写同一本总账时，如何既快、又不写错、又别爆内存。

我们真正要证明的事

不是“写了一个能跑的 CPU 程序”，而是证明它在真实网格上：组装结果正确、求解结果可对齐开源求解器、不同并行策略的速度和内存权衡有可复现证据。

当前系统怎么工作

项目主线代码在 `parallel_global_stiffness_assembly/cpu_parallel_stiffness_assembly`。现在它已经不是单个实验脚本，而是一套包含 CLI、测试、benchmark、验证导出和结果打包的实验平台。

A

读取网格

支持规则 Tet4/Hex8，也支持 Abaqus `.inp` 的 C3D4/C3D8。核心工程网格是 WindHub。

B

符号组装

先构造 CSR 稀疏结构和 scatter plan，只处理拓扑和写入位置，不算材料刚度。

C

数值组装

用 `linear_elastic_solid` 计算单元刚度，再用不同 CPU backend 写回全局矩阵。

D

验证与打包

输出 CSV/JSON/Markdown，保存 correctness、速度、内存生命周期和 RSS 证据。

当前技术判断

`cpu_atomic` 是 Intel full-host 上最值得作为主线展示的数值组装后端。`parallel_symbolic_reuse` 值得保留，因为它显著降低总耗时；但要明确说明它会增加临时内存和 isolated RSS。报告必须把 CSR/AssemblyPlan 持久内存、symbolic temporary、direct transient、backend extra memory、isolated RSS 分开看。

当前要避免的误解

  • !不要用 `legacy_synthetic` 结果讲正式结论；正式路径是 WindHub + `linear_elastic_solid`。
  • !不要把 estimated bytes 当成 measured RSS。RSS 的来源是 isolated-process runner。
  • !不要把 Apple QoS profile 和 Intel taskset/P/E 核 profile 当作同一种硬件控制。
