# CSC3 WindHub Linux 加速比复现与解释报告

## 1. 结论

Linux 复现实验确认：Windows 上约 $2.15\times$ 的总体加速不是单个平台异常。
在 Intel Core Ultra 7 265KF 的 20 个物理核心上，按 Windows Issue #54 相同的
fresh-process、未显式绑核口径，观测最优点为 $p=18$：

\[
S_{\mathrm{official}}(18)=2.431624,
\qquad
S_{\mathrm{candidate}}(1\rightarrow18)=2.748314.
\]

继续增加到 $p=20$ 后，两个加速比分别回落到 $2.383525$ 和 $2.693950$。
与 Windows 的共同点 $p=16$ 相比，Linux 的 official 加速为 $2.403351$，
Windows 为 $2.148994$；但两侧 candidate 自身的 $p=1\rightarrow16$ 缩放仅为
$2.716359$ 和 $2.673100$，非常接近。

仓库 formal runner 的绑核控制实验也没有改变结论。在
`OMP_PROC_BIND=close`、`OMP_PLACES=cores` 下，$p=20$ 的完整候选总时间中位数
为 1455.531 ms，official 加速为 $2.378876$，candidate 自身加速为
$2.817148$。绑核略微改善了 candidate 缩放，但总体仍约为 $2.4\times$。

低总体加速符合当前实现的计时边界和工作量：真正并行的 pattern、scatter 与
numeric atomic kernel 在稳定共同点 $p=16$ 分别只达到 $4.81\times$、
$3.69\times$ 和 $5.37\times$；两类未分项 residual 合计已占 $p=16$ 候选
总时间约 49.4%，reset 也几乎不随线程数缩短。此外，每次数值组装包含
86,867,352 次 atomic add。因而“符号阶段和数值阶段含有并行循环”并不等于
“两个阶段的完整 API 时间都能按核心数线性缩放”。

## 2. 实验问题与两个加速比

Windows 报告使用独立串行实现作为分母。为避免把“不同算法实现的基线差异”和
“同一候选实现的强缩放”混在一起，本报告同时给出两个比值：

\[
S_{\mathrm{official}}(p)
=
\frac{\operatorname{median}(t_{\mathrm{serial,total}},p=1\text{ child})}
{\operatorname{median}(t_{\mathrm{candidate,total}},p)},
\]

\[
S_{\mathrm{candidate}}(1\rightarrow p)
=
\frac{\operatorname{median}(t_{\mathrm{candidate,total}},p=1)}
{\operatorname{median}(t_{\mathrm{candidate,total}},p)}.
\]

前者严格复现 Windows 报告口径；后者更接近同一 candidate path 的强缩放。
Linux fresh-process 实验中，独立串行总时间中位数为 3634.677 ms，而 candidate
$p=1$ 总时间中位数为 4108.050 ms。candidate 单线程路径比独立串行实现多约
13.0% 的 OpenMP、atomic、数据结构和 API 开销，因此 official 加速天然低于
candidate 强缩放值。

## 3. 实验设计

### 3.1 Windows-mirror 主实验

- 源码：`94cd0d00f1d6725a6af67c8364b4bd07643f1e43` 的干净 detached worktree。
- 输入：materialized Git LFS 文件 `examples/3d-WindTurbineHub.inp`，SHA-256 为
  `4f3066b7e388ff0abaccb41d9ff5ec5a668e8d6ed008ae0c1061951f836ae0c3`，
  大小为 76,111,745 bytes。
- 规模：228,384 个节点、1,113,684 个 Tet4、685,152 个自由度、
  14,093,676 个 CSC3 非零元。
- 线程数：$p=1,2,\ldots,20$。
- 预热与重复：$W=2$、$R=7$。
- 进程模型：每个样本启动一个新进程；180 个子进程串行执行且时间不重叠。
- 顺序：每个正式轮次交替升序和降序，降低热状态与时间漂移对线程数的偏置。
- OpenMP：`OMP_DYNAMIC=false`，按样本设置 `OMP_NUM_THREADS=p` 与
  `OMP_THREAD_LIMIT=p`；不设置 `OMP_PROC_BIND` 或 `OMP_PLACES`，镜像 Windows
  的未显式绑核口径。
- 统计：只使用 140 个 `sample_kind=measured` 样本；每个 $p$ 恰好 7 个样本；
  标准差和变异系数使用总体定义。

Linux 与 Windows 的提交 SHA 不同，但对以下性能关键路径执行 Git tree 比较的
结果为 byte-identical：`include/`、`src/`、`tools/include/`、`tools/src/` 和
`run_windows_process_benchmark.py`。两侧输入 SHA-256、case size、$W$、$R$、
fresh-process 模型和交替顺序也一致。主机、编译器与 OpenMP runtime 不同，因此
只能比较缩放现象，不能把绝对耗时差异归因于单一平台因素。

### 3.2 绑核控制

绑核控制使用干净 detached SHA
`33918620e8689e745db2d81b5f52f659b3207075`；该提交只增加证据链 Python 修复，
没有改变 C++ 组装与 benchmark 核心。线程集为
$p\in\{1,2,4,8,16,20\}$，其余为 $W=2$、$R=7$、$m=1$，并设置：

```text
OMP_DYNAMIC=false
OMP_PROC_BIND=close
OMP_PLACES=cores
```

该控制的 formal runner manifest 为 `PASS`，configure、build、10 项 CTest、
benchmark 和三次 identity check 全部通过。不过规范 Linux runbook 还要求源码
提交已经合入 `origin/main`；当前 Issue 分支不满足该前提，也未执行候选包生成、
四方人工确认和 finalizer。因此它是技术控制证据，不是最终交付验收。

### 3.3 主机与工具链

- Ubuntu 24.04.4 LTS，Linux `7.0.0-28-generic`，`x86_64`。
- Intel Core Ultra 7 265KF，20 个逻辑 CPU、20 个物理核心、无 SMT、单 NUMA
  node；CPU 0--7 与 CPU 8--19 的 capacity 不同，是异构核心拓扑。
- GCC/G++ 13.3.0，CMake 3.28.3，Ninja 1.11.1，Python 3.11.15，GNU
  `libgomp.so.1`，`_OPENMP=201511`。
- 调速器为 `powersave`，boost 开启；运行中 CPU package 温度抽样约
  $60\text{--}61\,^{\circ}\mathrm{C}$。
- 机器存在少量桌面后台负载，不是隔离实验主机；因此所有结论均检查 $CV$，并
  不使用单次最佳值。

更完整的命令、二进制哈希、动态链接和 `/proc` 环境探针见
[execution-provenance.md](../../results/2026-07-29-linux-intel-issue-44/execution-provenance.md)。

## 4. 主实验结果

### 4.1 Linux 线程扫描

| $p$ | 候选总时间中位数 / ms | 总时间总体 $CV$ | $S_{\mathrm{official}}$ | $S_{\mathrm{candidate}}$ |
|---:|---:|---:|---:|---:|
| 1 | 4108.050 | 1.265% | 0.885 | 1.000 |
| 4 | 1982.590 | 0.502% | 1.833 | 2.072 |
| 8 | 1674.247 | 1.349% | 2.171 | 2.454 |
| 12 | 1569.908 | 1.122% | 2.315 | 2.617 |
| 16 | 1512.337 | 1.614% | 2.403 | 2.716 |
| 18 | **1494.753** | **1.263%** | **2.432** | **2.748** |
| 20 | 1524.917 | 1.040% | 2.384 | 2.694 |

$p=18$ 相比 $p=16$ 只缩短 17.585 ms，即 1.163%；相比 $p=20$ 缩短
30.164 ms，即 1.978%。因此 $p=18$ 只能称为本次 7 次中位数的观测最优点，
在没有置信区间或配对显著性检验时，不能声称它显著优于 $p=16$ 或 $p=20$。

所有线程点的候选总时间 $CV\le1.614\%$，低于 Issue #44 的 5% 门禁。180 个
进程样本的退出码、实际 team size、矩阵结构、有限值、scatter plan、样本身份、
调度顺序和时间不重叠检查均通过。

### 4.2 与 Windows 的共同点

| 平台与线程 | 独立串行中位数 / ms | 候选总时间中位数 / ms | 总时间总体 $CV$ | $S_{\mathrm{official}}$ | $S_{\mathrm{candidate}}$ |
|---|---:|---:|---:|---:|---:|
| Linux $p=16$ | 3634.677 | 1512.337 | 1.614% | 2.403 | 2.716 |
| Windows $p=16$ | 3069.451 | 1428.320 | 2.471% | 2.149 | 2.673 |

Linux 的 official 加速比比 Windows 高 11.836%，但 Linux 候选绝对时间反而慢
84.017 ms，即 5.882%。原因是两侧独立串行基线不同。更能反映 candidate 内部
缩放的 $S_{\mathrm{candidate}}$ 只相差 1.618%，两侧都约为 $2.7\times$。
因此证据支持的是“低缩放具有跨平台一致性”，而不是“Linux 绝对性能更高”。

### 4.3 绑核控制

| $p$ | 候选总时间中位数 / ms | 总时间总体 $CV$ | $S_{\mathrm{official}}$ | $S_{\mathrm{candidate}}$ |
|---:|---:|---:|---:|---:|
| 1 | 4100.446 | 0.213% | 0.844 | 1.000 |
| 8 | 1583.791 | 0.342% | 2.186 | 2.589 |
| 16 | 1458.182 | 0.254% | 2.375 | 2.812 |
| 20 | 1455.531 | 0.372% | 2.379 | 2.817 |

在 $p=20$，绑核相对未绑核把候选总时间从 1524.917 ms 降到 1455.531 ms，
约改善 4.55%；candidate 缩放从 $2.694\times$ 提高到 $2.817\times$。但是
official 加速仍为 $2.379\times$，说明线程放置不是总体低加速的主要解释。

## 5. 阶段分解

为满足 5% 稳定性门槛，阶段解释选择 Linux 与 Windows 的共同稳定点 $p=16$。
表中“阶段缩放”均为同一 candidate 阶段的 $p=1\rightarrow16$ 中位数比。

| 平台 / 阶段 | 中位数 / ms | 总体 $CV$ | candidate 阶段缩放 |
|---|---:|---:|---:|
| Linux symbolic pattern | 368.545 | 1.579% | 4.807 |
| Linux symbolic scatter | 319.576 | 3.284% | 3.688 |
| Linux symbolic residual | 592.215 | 0.909% | 0.991 |
| Linux numeric reset | 6.029 | 2.650% | 1.002 |
| Linux numeric kernel | 75.871 | 3.555% | 5.372 |
| Linux numeric residual | 154.881 | 3.193% | 1.014 |
| Windows symbolic pattern | 307.533 | 5.737% | 5.016 |
| Windows symbolic scatter | 134.934 | 3.714% | 7.258 |
| Windows symbolic residual | 674.595 | 1.002% | 0.938 |
| Windows numeric reset | 1.784 | 2.226% | 0.984 |
| Windows numeric kernel | 73.745 | 6.165% | 5.894 |
| Windows numeric residual | 234.056 | 3.002% | 1.007 |

Windows pattern 和 numeric kernel 的分项 $CV$ 略高于 5%，所以只用于机制说明，
不作为 formal 性能门禁的引用点。两侧真正并行的子阶段明显变快，但都远低于
$16\times$；两类 residual 与 reset 则几乎完全不缩放。

Linux $p=16$ 的 residual 合计中位数为 744.749 ms，占候选总时间 49.408%；
Windows $p=16$ 为 908.058 ms，占 63.624%。`residual` 只是“完整阶段时间减去
已分项计时”的差，包含串行工作、内存管理、OpenMP 区外工作与未单独计量开销，
不能把它逐字等同为不可优化的严格串行比例。

## 6. 为什么两个阶段都并行，总体仍只有两倍多

### 6.1 符号完整 API 只有三个区间并行

[`assembly_helper.cpp`](../../src/assembly_helper.cpp) 的
`build_symbolic_parallel()` 从输入校验前开始计 `symbolic_total_ms`。其中并行
区只覆盖：

1. 按列构造、排序并去重候选行；
2. 按列填充 CSC3 行索引；
3. 按单元查找 scatter 映射。

完整计时还包含串行的拓扑校验与规范化、DOF 邻接计数和填充、多个前缀和、逐列
`reserve`、CSC3 与 scatter 数组分配和初始化、失败检查及状态提交。实测
symbolic residual 在 $p=16$ 仍约 592 ms，和 $p=1$ 基本相同。方法名中的
“parallel”描述了局部实现，不代表整个 API 都处于 OpenMP 区内。

### 6.2 数值完整 API 不只是 atomic kernel

`assemble_numeric_atomic()` 的 `numeric_total_ms` 包含串行的布局校验、全部局部
矩阵有限性检查、上下三角对称性比较、全部 scatter target 合法性检查、临时数组
构造、整体数值数组清零、OpenMP team 管理和 atomic kernel。只有最后的按单元
scatter 循环处于 OpenMP 并行区。

对于本算例，每个 Tet4 有

\[
d_{\mathrm{local}}=4\times3=12
\]

个局部自由度，每个单元的上三角贡献数为

\[
N_{\triangle}=\frac{12\times13}{2}=78.
\]

因此每次完整数值组装执行：

\[
1{,}113{,}684\times78=86{,}867{,}352
\]

次 atomic add。完整 API 还扫描约 160,370,496 个局部矩阵值进行有限性检查，
比较 73,503,144 对上下三角值，检查 86,867,352 个 scatter target，并清零
14,093,676 个 CSC3 数值。该工作负载算术强度低、共享目标多，合理地受到内存
带宽、缓存一致性和 atomic 冲突限制。

本机 `perf_event_paranoid=4`，没有获得硬件计数器，因此“带宽饱和”和“缓存
一致性”是由源码与工作量支持的合理机制解释，而不是已经由计数器证实的唯一
根因。

### 6.3 官方数值加速不是完整 API 对完整 API

[`benchmark.cpp`](../../tools/src/benchmark.cpp) 的独立串行数值 baseline 会先在
计时外完成布局、有限性、对称性和 scatter 校验；被计时的部分只含串行清零和
非 atomic 普通加法。formal gate 的 `numeric_speedup` 再把它与 candidate 的
`numeric_reset_ms + numeric_kernel_ms` 比较，而不是与完整
`numeric_total_ms` 比较。

因此绑核控制中数值算法 gate 可在 $p=8$ 达到 $1.5\times$，并不意味着完整
数值 API 相对独立串行 baseline 也有同样加速。判断端到端组装成本必须查看
`numeric_total_ms` 和 `symbolic_total_ms` 的和。

### 6.4 Amdahl 模型显示损失不只来自 residual

只对同一 candidate 的强缩放做 Amdahl 反推，定义等效非缩放比例：

\[
f_{\mathrm{eff}}(p)
=
\frac{1/S_{\mathrm{candidate}}(p)-1/p}{1-1/p}.
\]

Linux $p=18$ 得到

\[
f_{\mathrm{eff}}(18)=32.6439\%,
\qquad
\frac{1}{f_{\mathrm{eff}}}=3.063.
\]

这不是严格串行代码比例；它同时吸收 residual、并行 kernel 的有限缩放、内存与
atomic 效应、线程调度和其他非理想开销。candidate $p=1$ 时 residual 只占
18.115%。如果把这 18.115% 全部假定为严格串行、其余工作理想按 18 线程缩放，
模型反而会预测 $S_{18}=4.412$，明显高于实测的 2.748。也就是说，仅指出
“有串行 residual”仍不够；三个已并行 kernel 只获得约 $3.7\text{--}5.4\times$
的有限缩放，同样是主要损失来源。

### 6.5 Windows SMT 与 Linux 异构核心只能解释边际平台化

Windows Ryzen 7 9800X3D 为 8 核 16 线程，$p>8$ 主要增加 SMT 线程；Linux
265KF 没有 SMT，但 20 个核心分属两个 capacity 层级，线程增加后调度器可能更多
使用较低 capacity 核。未绑核实验没有记录逐线程 CPU 落点，所以只能说 Linux 从
$p=12$ 起趋于平台、$p=20$ 回退与这一拓扑相容，不能据此确认具体调度路径。
绑核后总体仍约为 $2.4\times$，说明硬件线程类型最多解释平台区的边际变化，
不能替代前述软件计时边界与内存/atomic 分析。

## 9. 最终判断

本机 Linux 结果没有推翻 Windows 的低加速，反而复现了同一数量级：

\[
S_{\mathrm{official,max,Linux}}=2.432,
\qquad
S_{\mathrm{official,Windows},p=16}=2.149.
\]

更可比的 candidate 强缩放在共同点 $p=16$ 分别为 $2.716$ 和 $2.673$。这说明
约两倍多不是“Windows OpenMP 没真正并行”的证据，而是当前 CSC3 完整 API 的
并行覆盖率、固定/未分项工作、atomic 与内存型 kernel 的有限缩放，以及基线定义
共同作用的结果。若要显著提高总体加速，优先级应是：减少或缓存每次完整 API 的
重复验证与临时结构构造、并行化或复用前缀和与内存初始化、降低 8687 万次
atomic scatter 的冲突和带宽压力；单纯继续增加线程或只调整绑核策略，依据本次
数据不会带来数量级改变。
