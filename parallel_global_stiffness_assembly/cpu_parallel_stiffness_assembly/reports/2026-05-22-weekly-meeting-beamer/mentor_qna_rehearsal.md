# 2026-05-22 例会导师追问演练稿

这份材料用于会前口头演练，不是正式幻灯片正文。回答时以“我”为主体，先给一句直接结论，再补证据和边界。

## 一、符号组装是否真的并行

### 1. 你说符号组装已经并行化了，具体并行的是哪一部分？

**导师可能关心：** 我是否只是把数值组装并行结果说成了符号组装并行。

**建议回答：**
我并行化的是符号阶段里最关键的两个结构构建：第一是全局刚度矩阵的稀疏结构，也就是 CSR pattern；第二是数值组装时要用的写入计划，也就是 scatter plan。它们决定“哪些全局矩阵位置会非零”以及“每个单元矩阵条目最终写到全局矩阵哪里”。

我不是把数值计算伪装成符号并行。数值组装仍然是后续阶段，符号阶段会先独立生成可复用的结构信息。

**避免说法：** 不要只说“assembly 并行了”。要明确说是 symbolic assembly 中的 CSR pattern 和 scatter plan 并行构建。

### 2. 你怎么证明符号组装并行是值得做的？

**导师可能关心：** 并行符号阶段是否只是工程复杂度上升，并没有实际收益。

**建议回答：**
我这次用同一平台、同一 WindHub 算例、同一主线数值后端 `cpu_atomic` 做对比，只改变符号阶段是串行构建还是并行构建。

1 线程时几乎不值得，因为没有真正并行收益；但线程数增加后，符号阶段构建 CSR 和写入计划的墙钟时间明显下降。20 线程时，完整路径总时间从大约 `3644 ms` 降到 `917 ms`，约 `3.97x` 改善。

所以我的结论不是“任何情况下都值得”，而是：在 WindHub 这种大规模工程网格上，物理核心数足够时，符号阶段值得并行。

**避免说法：** 不要说“并行一定更好”。要说“多线程、大规模网格下值得；1 线程下不值得”。

### 3. 这个加速是不是只因为数值组装也变快了？

**导师可能关心：** 图里的总时间是否混入了数值后端影响。

**建议回答：**
不是。我这里的关键对比是同一数值后端、同一线程数，只切换符号阶段的构建方式。这样可以把变量收敛到“符号阶段是否并行”。

图 1 和图 2 的作用就是避免泛泛比较不同算法，而是在同一数值后端下看 serial symbolic build 和 parallel symbolic build 的差异。

**避免说法：** 不要把不同 backend 的曲线直接拿来证明符号阶段收益。

### 4. 为什么 1 线程并行符号不值得？

**导师可能关心：** 并行算法是否有额外开销。

**建议回答：**
1 线程时并行算法没有多核分摊收益，反而还有并行框架、临时数据结构和调度逻辑的开销。表格里 1 线程下串行符号和并行符号总耗时几乎一样，所以我不会说 1 线程也值得。

我的判断是：并行符号构建主要面向多核心机器和大规模网格，不是为了优化单线程路径。

### 5. 并行符号组装用了什么算法思路？

**导师可能关心：** 并行方式是否确定、是否可复现、是否适合 CSR。

**建议回答：**  
它不是简单给原来的串行循环加锁，而是把符号阶段拆成可以并行处理的结构构建问题。

核心思路是：用节点和自由度邻接关系构造 CSR 稀疏模式；用 row-owned 的方式统计和填充每一行，避免多个线程随意写同一行结构；对 scatter plan 使用按单元预分配的切片，让每个单元的写入位置可以并行生成；最后保证并行结果和串行符号结果在 `row_offsets`、`col_indices`、`dofs`、`scatter` 上严格一致。

一句话概括：我采用的是“先把全局稀疏结构按行确定，再把单元写入映射并行生成”的确定性并行算法。

### 6. 为什么不用更简单的全局锁或者并发集合来构建符号结构？

**导师可能关心：** 当前实现是否过度复杂。

**建议回答：**  
符号阶段的目标不是只要“能跑”，而是要稳定、可复现、可和串行结果精确对齐。全局锁或者并发集合会带来锁竞争、内存行为不可控、结果顺序可能不稳定等问题，后续还需要排序和去重。

我现在的做法更贴近 CSR 的最终存储形式：按行统计、按行填充、按单元生成 scatter。这样最后生成的结构天然适合数值组装复用，也方便和串行符号结果做精确一致性测试。

## 二、符号组装与数值组装是否解耦

### 7. 符号组装和数值组装现在是否已经解耦？

**导师可能关心：** “解耦”是不是被说得过满。

**建议回答：**  
当前实现上已经把符号结构构建和数值计算解耦了。符号阶段生成 CSR pattern 和 scatter plan；数值阶段只需要沿着这些结构计算并累加数值。

但我会强调一个边界：这是工程实现上的解耦，不是说两者毫无关系。数值组装仍然依赖符号阶段给出的写入位置，只是不再每次重新构建这些结构。

### 8. 你怎么定义符号组装和数值组装之间的耦合度？

**导师可能关心：** “解耦”的评价标准是否清楚。

**建议回答：**  
我会从三个层面定义耦合度。

第一是数据依赖耦合：数值阶段是否必须读取符号阶段产物。如果需要 CSR pattern 和 scatter plan，就是有数据依赖。

第二是重建耦合：每做一次数值组装，是否必须重新做一次符号组装。如果可以复用符号结果，重建耦合就低。

第三是性能耦合：符号阶段的耗时和内存是否会显著影响完整组装路径。如果符号构建占比很高，那么性能耦合强；如果符号结果可以摊销到多次数值组装，性能耦合就降低。

所以我说“解耦”的准确含义是：数值阶段仍依赖符号产物，但不再必须和符号构建绑定在同一次流程里重复执行。

## 三、数值组装如何复用符号结果

### 9. 数值组装阶段具体如何利用 CSR 和 scatter？

**导师可能关心：** 符号组装产物是否真的被数值阶段复用，还是只是报告里的术语。

**建议回答：**
符号阶段先把全局矩阵的 CSR 骨架和每个单元局部条目的 scatter 写入位置算好。数值阶段不再查找稀疏位置，只负责计算单元刚度矩阵 `Ke`，然后根据 scatter 把 `Ke(i,j)` 加到对应的 CSR `values[p]`。

具体来说，CSR 决定全局矩阵的存储骨架，`row_offsets` 和 `col_indices` 固定非零元位置；scatter plan 则把每个单元的局部条目提前映射到 `values[p]`。数值阶段的核心循环就是“算 `Ke`，读 scatter，累加到 `values[p]`”。

**避免说法：** 不要说“数值阶段重新生成稀疏结构”。当前主线是复用 CSR/scatter。

### 10. atomic、lock_guard、private_csr、graph_coloring、row_owner 的区别是什么？

**导师可能关心：** 五类后端是否真的不同，还是只是实现名字不同。

**建议回答：**
它们的共同点是都复用同一套 CSR 和 scatter。区别不在矩阵格式，而在多个线程同时想写同一个 `values[p]` 时如何处理冲突。

`cpu_atomic` 是所有线程直接写共享 `values[p]`，但每次写入用 atomic 加法保护。`cpu_lock_guard` 也是共享写入，但每个非零元配一把 mutex，写之前先加锁。`cpu_private_csr` 则让每个线程写自己的 `values` 副本，最后把所有副本逐项加回总矩阵。`cpu_graph_coloring` 先把互不冲突的单元分到同一颜色组，组内并行写全局矩阵而不加锁。`cpu_row_owner` 按 CSR 行分配 owner，每个线程只写自己拥有的行。

**一句话总结：** atomic 用原子操作，lock_guard 用锁，private_csr 用内存换同步，graph_coloring 用分批避免冲突，row_owner 用行所有权避免冲突。

### 11. 这五类数值后端里，为什么当前主线更偏向 atomic？

**导师可能关心：** 主线后端选择是否只是实现偏好。

**建议回答：**
在这组 Intel full-host 结果中，`cpu_atomic` 的综合表现最好：速度快，额外后端内存为 0。`cpu_private_csr` 可以减少写冲突，但线程越多私有 `values` 数组越大；`cpu_lock_guard` 能作为 C++ 标准锁基线，但 per-entry mutex 的内存和加锁开销都明显；`cpu_graph_coloring` 避免了组内冲突，但有着色预处理和颜色组负载问题；`cpu_row_owner` 是很有价值的候选路线，但会引入任务列表和可能的重复 `Ke` 计算。

所以我这次把 `cpu_atomic` 作为主线，不是因为其他后端不重要，而是因为它在当前证据下速度和内存的平衡最好。

## 四、正确性证据链

### 12. 正确性是不是每一轮都验证了？参考矩阵是什么？

**导师可能关心：** 是否存在只看性能、不看结果正确性的测试。

**建议回答：**  
当前正式参考矩阵是 C++ `cpu_serial` 组装出的矩阵。每一类候选路径，比如并行符号复用、直接无符号组装、不同数值后端，都会和这个 C++ 串行参考矩阵比较。

我使用的误差指标主要是 `relative_l2` 和 `max_abs`。`relative_l2` 看整体相对误差，`max_abs` 看单个矩阵条目的最大绝对差异。当前结果里 `relative_l2` 大约在 `1e-16` 量级，说明数值上和串行参考高度一致。

### 13. 为什么不用 Abaqus 或 MATLAB 的矩阵作为正确性参考？

**导师可能关心：** 项目内 reference 是否足够独立。

**建议回答：**  
这次我没有把 Abaqus/MATLAB 外部参考矩阵纳入已完成证据。原因是外部矩阵导入需要明确自由度排序、边界条件、材料参数、单元积分方式和矩阵导出格式，否则很容易比较的是两个不同约定下的矩阵。

所以我现在采用更可控的项目内 reference：C++ `cpu_serial`。Abaqus/MATLAB 外部矩阵验证是下一步交叉验证项，而不是这次已经完成的证明。

**避免说法：** 不要因为有 MATLAB spy 图就说“已经用 MATLAB 验证正确性”。

### 14. MATLAB 图有什么作用？是不是正确性验证？

**导师可能关心：** 幻灯片里的 MATLAB 图是否被误用为外部正确性证据。

**建议回答：**  
MATLAB 图在这份报告里不是数值正确性 reference。它的作用是稀疏结构可视化核对，也就是看组装后的整体刚度矩阵非零模式是否一致。

我会特别说明：MATLAB 当前用于 sparse pattern 可视化，不用于证明数值矩阵来自外部正确参考。数值正确性仍然以 C++ `cpu_serial` 矩阵为 reference。

### 15. 之前 Python 和 MATLAB 稀疏图对角方向相反，这说明矩阵不一致吗？

**导师可能关心：** 可视化差异是否暴露数据错误。

**建议回答：**  
不说明矩阵不一致。那是绘图坐标约定的问题，不是 CSR 数据本身的问题。

整体刚度矩阵有确定的行列坐标表示。Python 和 MATLAB 如果一个把行号向下画、另一个把行号向上画，就会出现视觉上对角方向相反。现在我已经把两者统一成同一约定：行号向下、列号向右、非零元为黑点。所以两张图现在反映的是同一个确定矩阵表示。

### 16. 为什么导师图是带状，而我的 WindHub 原始图像是块状？

**导师可能关心：** 块状图是否说明整体刚度矩阵构造错了。

**建议回答：**
这不说明矩阵构造错误。导师图里的 `B(p,p)` 通常表示矩阵经过排列向量 `p` 重排序之后的显示结果。我的原始图直接使用 `.inp` 文件里的节点顺序，而 HyperMesh/Abaqus 导出的节点顺序不是带宽优化顺序，所以会呈现块状聚簇。

我新增了同一 CSR pattern 的 RCM 重排序可视化，也就是 `K(p,p)`。重排序后非零数仍是 `27,502,200`，但带宽从 `392,948` 降到 `9,314`，图像呈现带状稀疏。这说明差异主要来自自由度编号顺序，而不是组装算法错误。

**避免说法：** 不要说“我把 benchmark 矩阵重排了”。RCM 只用于可视化解释，当前数值 benchmark 仍使用原始 CSR/scatter 口径。

### 17. 除了 spy 图，为什么新增 CSR 三数组展示？

**导师可能关心：** 稀疏图是否只是视觉检查，缺少真实数据结构解释。

**建议回答：**  
spy 图只能展示“哪里非零”，但不能展示组装后的矩阵在内存里到底怎么存。

CSR 三数组展示的是更底层、更确定的表示方式：`row_offsets` 定位每一行非零元在数组里的起止位置；`col_indices` 给出这些非零元所在的列；`values` 存储真正组装后的刚度值。

我只展示局部窗口，是因为 WindHub 全矩阵有 `27,502,200` 个非零元，不适合放进幻灯片。局部窗口足够说明存储机制。

## 五、内存与直接无符号组装

### 18. 无符号直接组装为什么会有 2.39 GiB 临时内存？

**导师可能关心：** “无符号”是否应该天然更省内存。

**建议回答：**  
无符号直接组装不预先复用 CSR pattern 和 scatter plan，它需要先生成大量单元贡献项，然后再做排序、归并和规约。这个贡献数组就是 2.39 GiB 的主要来源。

所以“无符号”不等于“低内存”。它省掉的是常驻符号结构，但换来了巨大的 transient contribution buffer，也就是临时贡献缓冲。

### 19. symbolic+numeric 和 direct/no-symbolic 的内存区别是什么？

**导师可能关心：** 内存表里的 persistent、transient、RSS 是否混在一起。

**建议回答：**  
symbolic+numeric 路线的内存主要分成：CSR 结构、scatter plan、输出矩阵数值数组，以及少量临时构建缓冲。这些结构有一部分可以复用，是常驻意义更强的内存。

direct/no-symbolic 路线不保留符号结构，但需要一次性生成大量贡献项再排序归并，所以 transient memory 很高。2.39 GiB 指的就是这类临时贡献缓冲，不应该和 RSS 或常驻结构内存混为一个概念。

### 20. 为什么主线数值后端选择 `cpu_atomic`？

**导师可能关心：** 主线 backend 是否只是实现方便。

**建议回答：**  
因为在这组 Intel 全核心结果里，`cpu_atomic` 的速度最好，同时额外后端内存为 0。

`cpu_private_csr` 会为每个线程维护私有矩阵，内存随线程数增长；`cpu_lock_guard` 每个非零条目需要 mutex，内存和同步开销都比较重。`cpu_atomic` 在当前问题规模下是速度和内存的综合最优主线。

### 21. `cpu_lock_guard` 的意义是什么？既然慢，为什么还做？

**导师可能关心：** 是否有必要保留一个表现不好的算法。

**建议回答：**  
`cpu_lock_guard` 的意义是作为对照基线，而不是作为推荐主线。它用每个矩阵条目的 mutex 来保护写入，可以帮助我们回答一个问题：如果不用 atomic，而是用更传统的 per-entry lock，会发生什么？

结果显示它通常不是最优选择，但它能作为 appendix data，证明我们不是只比较了一个自己偏好的方法，而是把同步策略的代价也量化了。

## 六、证据边界与下一步

### 22. 你的结果是单次扫描，可信度够吗？

**导师可能关心：** 当前结果是否已经达到最终论文级统计证据。

**建议回答：**  
这次 Linux Intel full-host 结果是单次全核心扫描，所以我不会把它说成最终统计结论。它足以支撑阶段性判断：并行符号阶段在大规模 WindHub 上有明显收益，direct/no-symbolic 有较大临时内存压力。

但如果要形成最终论文级结论，下一步应该做 repeat=3 或更多重复，报告均值、方差或置信区间。

### 23. 为什么线程范围是 1 到 20？

**导师可能关心：** 线程范围是否任意选取。

**建议回答：**  
因为这台 Linux Intel 测试机是 20 个物理核心，并且物理/逻辑核心数都是 20/20。这里我想回答的是“随着物理核心数增加，符号阶段是否值得并行化”，所以线程范围设为 1 到 20。

这次没有做 P-core/E-core 隔离，也没有跨平台混合解释。Apple 平台结果可以作为补充，但这份 deck 的主证据固定在 Linux Intel。

### 24. 下一步最应该补什么？

**导师可能关心：** 当前工作如何继续形成更强证据链。

**建议回答：**  
我认为下一步有两个自然补强方向。

第一，补外部参考矩阵验证。也就是把 Abaqus 或 MATLAB 导出的正确矩阵按同一自由度排序和边界条件导入，再和 C++ 结果比较。这样可以把 correctness 从项目内 reference 扩展到外部交叉验证。

第二，把当前 symbolic memory 实验扩展成多次重复，形成更稳定的统计证据。现在单次结果已经能看出趋势，但最终汇报最好有 repeat 平均和波动范围。

## 会前主动防守句

如果导师开始追问前有机会，我可以先说：

> 这次我把证据分成三层：第一层是性能，回答符号阶段是否值得并行；第二层是正确性，当前以 C++ `cpu_serial` 为正式参考矩阵；第三层是内存生命周期，区分常驻结构、临时缓冲和操作系统观察到的 RSS。MATLAB 当前只用于稀疏结构可视化，不作为外部正确矩阵 reference。
