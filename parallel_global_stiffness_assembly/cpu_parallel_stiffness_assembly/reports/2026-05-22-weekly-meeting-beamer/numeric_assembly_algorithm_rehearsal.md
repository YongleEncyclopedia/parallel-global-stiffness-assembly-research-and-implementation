# 数值组装如何复用 CSR 与 scatter：五类并行后端讲解稿

这份材料用于解释数值组装阶段的具体工作方式。面向例会问答时，先讲共同机制，再讲不同后端如何处理并发写冲突。

## 一、符号组装给数值组装留下了什么

符号组装阶段不计算刚度值，它只提前回答两个问题：

1. 全局刚度矩阵哪些位置可能非零。
2. 每个单元局部刚度矩阵 `Ke(i,j)` 应该加到全局矩阵的哪个位置。

当前 C++ 实现里，符号阶段主要留下两类结构。

### 1. CSR：全局矩阵的压缩骨架

完整刚度矩阵很大，但大部分位置是零，所以不存完整二维矩阵，而是用 CSR 存非零元：

- `row_offsets`：每一行非零元从哪里开始、到哪里结束。
- `col_indices`：每个非零元位于哪一列。
- `values`：数值组装真正要填入的刚度值。

可以把 CSR 理解成“已经画好格子的账本”：格子位置已经确定，但格子里的数值还没填。

### 2. scatter plan：局部条目到全局槽位的地址表

对一个四节点四面体单元，每个节点有 3 个自由度，所以一个单元有 12 个自由度，局部刚度矩阵 `Ke` 是 `12 x 12`。

符号阶段会提前查好：

```text
Ke(0,0) -> CSR values[p0]
Ke(0,1) -> CSR values[p1]
...
Ke(i,j) -> CSR values[p]
```

所以数值阶段不需要再查“全局矩阵第 r 行第 c 列存在哪里”，只需要按 `scatter` 给出的 `p` 直接写 `values[p]`。

一句话概括：

> CSR 决定全局矩阵的存储骨架；scatter plan 决定每个局部刚度条目写到骨架里的哪个槽位。

## 二、所有数值后端共享的基本流程

所有后端的数学动作都一样：

```text
for 每个单元 e:
    计算这个单元的局部刚度矩阵 Ke
    读取这个单元的 scatter 地址表
    把 Ke(i,j) 累加到 CSR values[scatter(i,j)]
```

真正不同的是并行冲突处理方式。多个相邻单元可能同时给同一个全局自由度位置贡献数值，因此多个线程可能同时写同一个 `values[p]`。

五类并行数值后端的核心区别就是：

> 当多个线程都想写同一个 CSR 槽位 `values[p]` 时，如何保证结果不被写坏。

## 三、`cpu_atomic`：共享矩阵，原子加法保护每次写入

### 工作方式

多个线程并行遍历单元。每个线程计算自己负责单元的 `Ke`，再通过 scatter 找到目标位置 `p`，执行原子加法：

```text
atomic values[p] += Ke(i,j)
```

### 通俗理解

所有人都往同一本账本上记账，但每次改某一格时，用一个很轻量的“原子写入”保证这次加法不会被其他人打断。

### 如何使用 CSR/scatter

- CSR 提供共享的最终 `values` 数组。
- scatter 给出每个 `Ke(i,j)` 的目标槽位 `p`。
- atomic 保护 `values[p] += v`。

### 优缺点

优点是实现简单、额外内存几乎为零、当前主线结果表现好。缺点是热点位置会产生原子争用，线程数很高时可能受同步和缓存一致性影响。

## 四、`cpu_lock_guard`：共享矩阵，每个非零元一把锁

### 工作方式

`prepare()` 阶段为每个 CSR 非零元分配一个 `std::mutex`。数值组装时，每个线程计算 `Ke`，通过 scatter 找到目标 `p`，写入前锁住 `mutex[p]`，写完释放。

```text
lock mutex[p]
values[p] += Ke(i,j)
unlock mutex[p]
```

### 通俗理解

所有人仍然写同一本账本，但账本每一格旁边都有一把锁。谁要改这一格，先拿锁，改完再放锁。

### 如何使用 CSR/scatter

- CSR 的 `nnz` 决定需要多少把锁。
- scatter 给出目标槽位 `p`。
- `mutex[p]` 保护对应的 `values[p]`。

### 优缺点

优点是语义直观，能作为 `atomic` 的同步对照组。缺点是每个非零元一把锁，内存开销大；加锁/解锁通常比 atomic 更重，所以它不是预期最优路线。

## 五、`cpu_private_csr`：每个线程写自己的 values，最后归并

### 工作方式

每个线程分配一整份私有 `values` 数组，但 CSR 行列结构仍然相同：

```text
private_values[thread_id][p] += Ke(i,j)
```

全部线程完成后，再对每个 CSR 位置做归并：

```text
values[p] = sum(private_values[t][p] for all t)
```

### 通俗理解

每个人先在自己的账本上记账，不互相抢。最后把所有人的账本逐格加起来，得到总账。

### 如何使用 CSR/scatter

- 所有私有数组沿用同一套 CSR 非零结构。
- scatter 仍然给出目标槽位 `p`。
- 区别是写到 `private_values[tid][p]`，不是直接写全局 `values[p]`。

### 优缺点

优点是数值组装阶段没有共享写冲突，不需要 atomic 或锁。缺点是额外内存约为：

```text
threads x nnz x sizeof(double)
```

线程越多，私有数组越多；最后逐项归并也有成本。

## 六、`cpu_graph_coloring`：把不会冲突的单元分成同一颜色

### 工作方式

如果两个单元共享节点，它们可能写到相同全局自由度位置，因此不能放在同一批无锁并行执行。图着色会先把单元分成若干颜色组：

- 同一颜色组内部的单元互不共享节点。
- 同一颜色组可以并行写全局矩阵。
- 不同颜色组之间顺序执行。

### 通俗理解

像安排学生到黑板写答案。可能写同一块区域的学生不能同时上去；不会互相影响的一组学生可以一起上。

### 如何使用 CSR/scatter

- CSR 仍然是最终全局矩阵。
- scatter 仍然告诉每个 `Ke(i,j)` 写到哪个 `values[p]`。
- 图着色保证同一颜色组内不会同时写同一个位置，因此组内写入不需要 atomic 或锁。

### 优缺点

优点是组内并行没有写冲突，也不需要复制整份矩阵。缺点是着色有预处理成本，颜色数和颜色组大小会影响负载均衡。

## 七、`cpu_row_owner`：谁拥有这一行，谁负责写这一行

### 工作方式

全局 CSR 矩阵按行分给不同线程 owner。每个线程只写自己拥有的行。`prepare()` 阶段会把每个局部条目转换成任务：

```text
(element, local_i, local_j, csr_index)
```

然后根据这个条目对应的全局行，把任务放进对应 owner 的任务桶。

### 通俗理解

不是按“单元”分工，而是按“账本页码”分工。每个人只负责自己那几页账本，所以不会和别人同时写同一页。

### 如何使用 CSR/scatter

- CSR 的行号决定 owner 分区。
- `AssemblyPlan::dofs` 告诉局部行 `local_i` 对应哪个全局行。
- scatter 给出最终 `csr_index`。
- owner 线程只处理属于自己行范围的任务。

### 优缺点

优点是不需要 atomic、不需要 per-entry mutex，也不需要每个线程复制完整 `values`。缺点是一个单元如果跨多个 owner，可能被多个 owner 重复计算 `Ke`；任务列表也会带来额外内存。

## 八、五类算法的核心区别

| 算法 | 谁写全局 `values[p]` | 如何避免冲突 | 主要代价 |
| --- | --- | --- | --- |
| `cpu_atomic` | 所有线程直接写 | 原子加法 | 同步争用 |
| `cpu_lock_guard` | 所有线程直接写 | 每个非零元一把锁 | 锁开销和 mutex 内存 |
| `cpu_private_csr` | 每个线程写自己的 values | 私有数组，最后归并 | `threads x nnz` 内存和归并成本 |
| `cpu_graph_coloring` | 同一颜色组并行写 | 保证组内单元不冲突 | 着色成本和颜色组负载不均 |
| `cpu_row_owner` | 每个线程只写自己拥有的行 | 行 owner 分区 | 任务列表内存和可能重复计算 `Ke` |

共同点是：它们都复用符号阶段的 CSR 结构和 scatter plan。区别不是“矩阵格式不同”，而是“并发写入冲突如何处理”。

## 九、补充：`cpu_coo_sort_reduce`

当前仓库还实现了 `cpu_coo_sort_reduce`。它不直接写最终 `values[p]`，而是先生成很多贡献项：

```text
(csr_index, value)
```

scatter 在这里仍然有用，因为它给出的正是 `csr_index`。后端先保存小票，再按 `csr_index` 排序，把同一个位置的贡献加起来。

通俗理解：不是直接写账本，而是每个人先写小票，小票上写“第 p 格加多少钱”。最后把所有小票按 p 排序，同一格的小票加起来，填到账本里。

它的优点是生成阶段没有共享写冲突；缺点是中间贡献数组很大，排序和归并成本高。当前定位更像研究对照组，不是主线最优后端。

## 十、例会中可以直接复述的版本

如果导师问“数值组装怎么利用符号组装结果”，我可以这样回答：

> 符号阶段先把全局矩阵的 CSR 骨架和每个单元局部条目的 scatter 写入位置算好。数值阶段不再查找稀疏位置，只负责计算单元刚度矩阵 `Ke`，然后根据 scatter 把 `Ke(i,j)` 加到对应的 CSR `values[p]`。不同 CPU 后端的区别，不在于是否使用 CSR/scatter，而在于多个线程同时写同一个 `values[p]` 时如何处理冲突：`atomic` 用原子加法，`lock_guard` 用每个 entry 的锁，`private_csr` 用线程私有数组再归并，`graph_coloring` 先把无冲突单元分批，`row_owner` 则让每个线程只写自己拥有的矩阵行。
